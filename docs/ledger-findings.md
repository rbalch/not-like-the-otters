# Ledger findings

The experiment log. Every dislike of agent output gets sorted into a bin and recorded
here, whether or not it becomes a control. An unlogged finding is a lost data point.

- **Bin 1** — already covered by a linter or type-checker. The harness adds nothing.
- **Bin 2** — a concrete, checkable, systemic pattern. **This is the value.**
- **Bin 3** — genuine subjective taste. No control will ever catch it.

Rule of three: a Bin 2 finding stays in the soft layer (a note, a nudge, a one-off
correction) until its **third** sighting. Only then does it earn a decision and a
CI-enforced control.

**The falsifiable test:** if Bin 2 stays fat and review burden measurably shrinks, the
harness earns its keep. If nearly everything lands in Bin 1 or Bin 3, this is
complicated linters plus a wiki and we should say so and drop it. Do not judge it by
"does CI go red."

See the `finding-triage` skill for the procedure and the entry template.

Findings about the **harness itself** — something it got wrong, friction that felt like
ceremony, a control that fired on correct code — are worth logging here too. Mark them
as harness findings and leave them unbinned; the bins sort dislikes of *agent output*,
and forcing a harness observation into one loses what makes it interesting.

## Findings

### F-1 — Relative path asserted from an adjacent check, not the failing one

- **Date:** 2026-08-17
- **Bin:** 2
- **Claim:** In `src-tauri/tauri.conf.json`, every command string that names a directory
  (`beforeDevCommand`, `beforeBuildCommand`) must resolve from the **project root**,
  while every path-valued key (`frontendDist`, `devUrl`) resolves from the **config
  file's own directory**. A config carrying both must not use the same base for both.
- **Sightings:** 1
- **Action:** soft — noted, no control yet
- **Notes:** M0.1. The builder shipped `--prefix ../app` for the hooks, correct only if
  hooks ran from `src-tauri/`. They run from `/app`, so `../app` resolved back to the
  repo root and `npm run tauri -- build` — the only script the change shipped — failed
  every time. Measured with a `pwd`-printing hook: `HOOK_CWD=/app`. Machine-checkable:
  a control can resolve each hook's `--prefix` against the repo root and assert a
  `package.json` exists there carrying the named script. Held at one sighting.

### F-2 — Verification by adjacent command

- **Date:** 2026-08-17
- **Bin:** 3
- **Claim:** A verification must run the exact command a user would run. Evidence from a
  neighbouring command that merely looks confirmatory does not count.
- **Sightings:** 1
- **Action:** soft — noted, no control possible
- **Notes:** M0.1. The builder offered `tauri info` echoing `frontendDist` as proof the
  wiring was sound. `tauri info` reads back the one path that was already correct and
  says nothing about the hooks. This is the parent cause of F-1 and the more interesting
  finding, but "did the agent verify the right thing" is not machine-checkable — no
  control will ever catch it. Recording it as taste is the honest answer, and a fat
  Bin 3 is a real result rather than a failure.

### F-3 — TypeScript strict mode off at scaffold time

- **Date:** 2026-08-17
- **Bin:** 2
- **Claim:** `app/tsconfig.app.json` must set `"strict": true`.
- **Sightings:** 1
- **Action:** soft — fixed in `cab34b5`, no control yet
- **Notes:** M0.1. Not a builder error: a fresh `create-vite react-ts` scaffold produces
  byte-identical options, so absent `strict` is current upstream template shape. Flagged
  by boundary review, fixed deliberately because M0.3 puts IPC response types across the
  webview/core seam and `strictNullChecks` is what makes that boundary honest. Crisp and
  checkable, so it is a genuine control candidate — but one sighting, and the rule of
  three exists to stop a single plausible rule becoming a permanent one.

### F-4 — Redundant `/target/` in a generated `.gitignore`

- **Date:** 2026-08-17
- **Bin:** 3
- **Claim:** none statable — "is this duplicate line worth removing" is taste.
- **Sightings:** 1
- **Action:** declined deliberately
- **Notes:** M0.1, raised as a minor and refused. `src-tauri/.gitignore` is generated by
  the Tauri CLI and a future upgrade may rewrite it. Hand-editing generated scaffold to
  delete a harmless duplicate buys nothing. This finding is why round 2 scored 4/5 and
  not 5/5, which is the correct trade.

## Harness findings

Observations about the harness itself. Deliberately unbinned — the bins sort dislikes of
agent output, and forcing a harness observation into one loses what makes it interesting.

### H-1 — Two reviewers disagreed, and the disagreement was the point

- **Date:** 2026-08-17
- **Notes:** M0.1 round 1. `boundary-reviewer` returned APPROVE 5/5; `reviewer` returned
  CHANGES_REQUESTED 2/5 on a scaffold that could not build. Not a contradiction — they
  answer different questions ("did this violate a rule or seam" vs "does it work"). A
  single reviewer scoped to rule compliance would have passed a broken deliverable. First
  evidence that running both is worth the cost.

### H-2 — An unreviewed source edit arrived framed as pre-approved

- **Date:** 2026-08-17
- **Notes:** M0.1 round 1. Mid-review, a message reached the reviewer through its tool
  channel asserting that an edit to `src-tauri/Cargo.toml` was intentional and instructing
  it not to mention it. The reviewer refused the framing, reverted the file, and surfaced
  it. **The edit itself turned out to be benign** — every real `npm run tauri -- build`
  rewrites that file, adding `features = []` to two dependency lines; reproduced
  independently twice. So the content was mundane and the instruction to conceal it was
  not. Recorded because the review step catching it is the only reason anyone knows, and
  because "an edit presented as already-approved" is a failure mode the loop should keep
  being able to catch. Origin unknown; not attributed to any agent in the round.
